# 6. Failure Scenarios: Detection, Recovery, Mitigation

Scenarios 1, 3, and 6 in the table below are backed by automated chaos tests in `test/chaos/` that exercise them against real compiled binaries, not just design reasoning; see that directory's README for what each script proves and how to reproduce it. Scenario 4's Redis-outage row describes a Postgres-polling fallback for job submission and rate limiting; the fallback poller for orphaned queued jobs was not implemented (see `internal/api/handlers_jobs.go`'s own comment on this gap), and rate limiting does not exist anywhere in the current system. Scenario 13's read-replica row describes the original target architecture; no read replica exists in local development.

The rule this whole system follows: **Postgres transactions are the only place correctness is allowed to live.** Redis, gRPC streams, and in-memory state are all allowed to be wrong, stale, or momentarily lost, because every one of them can be reconciled back to Postgres. Keep that in mind as the reasoning behind almost every row below.

| # | Scenario | Detection | Recovery / Mitigation |
|---|---|---|---|
| 1 | **Scheduler leader crashes** | Postgres advisory lock session drops (tied to the leader's DB connection); lock becomes acquirable immediately. Standby replicas poll for the lock every 1–2s. | A standby acquires the lock and becomes leader within ~1-2s. Any jobs the old leader had claimed from the Redis stream but not yet committed sit in the Pending Entries List; new leader runs an `XCLAIM` sweep on startup for entries pending >10s and reprocesses them. Any assignment that *did* commit to Postgres before the crash is already durable and simply continues (worker is already BUSY, job already ASSIGNED, nothing to redo). |
| 2 | **Scheduler crashes mid-assignment transaction** (between `BEGIN` and `COMMIT` in 5.4) | N/A at the DB level: Postgres transactions are atomic. Either the whole `workers`+`jobs` update lands or none of it does. | Nothing to recover: the transaction rolled back automatically. The job remains QUEUED (or, worst case, its stream entry is in the PEL, recovered by the XCLAIM sweep above) and gets picked up again on the next scheduling tick, by whichever replica is leader. |
| 3 | **Worker crashes** (process dies, host dies, OOM-killed) | No heartbeat for 20s → dead-worker reaper (doc 5.3) marks it DEAD via the authoritative Postgres sweep. | In-flight job(s) on that worker are requeued in the same transaction that marks the worker DEAD (atomic: never "worker dead, job still shows RUNNING forever"). Requeued job goes through the normal retry-policy path (doc 9) rather than infinite immediate resubmission. |
| 4 | **Redis outage (total)** | Scheduler's Redis client health-checks fail; `/readyz` reports `redis: false`. | **Job queue:** falls back to a Postgres-polled queue: the scheduler issues `SELECT ... WHERE status='QUEUED' ORDER BY priority, created_at FOR UPDATE SKIP LOCKED LIMIT N` directly against Postgres (the same index, `idx_jobs_queued_priority`, serves this). Slower and higher-latency than Streams, but correct and available. **Hot-path worker cache:** scheduler falls back to querying `workers` directly (same partial index), again slower, but the fleet keeps scheduling. **Locks:** the `lock:job:{id}:assign` Redis lock is skipped; the Postgres CAS (`WHERE status='READY'`) is the real correctness guarantee anyway (doc 5.4), so losing the advisory lock only risks a few wasted retries under contention, not a double-assignment. **Rate limiting:** registration rate limiting fails open (logged, alarmed) rather than failing closed and blocking all worker registration: availability of the fleet is prioritized over this specific abuse control during a known outage. Recovery is automatic once Redis returns; no manual reconciliation needed because Redis never held anything that wasn't reconstructable from Postgres. |
| 5 | **PostgreSQL outage (primary unreachable)** | Health checks fail; `/readyz` reports `postgres: false` on all replicas. | This is the one true hard dependency: no new assignments can be safely made without the CAS guarantee, so the scheduler **stops making new assignments** rather than risk unguarded double-booking, but continues to: accept heartbeats (buffered in Redis, drained to Postgres once it recovers), keep already-running jobs running (workers don't need the scheduler mid-build), and serve reads from cache where possible. On the API side, `POST /jobs` returns `503` rather than silently dropping submissions. This is a deliberate trade-off: brief unavailability of new scheduling beats corrupting the fleet's state. Mitigated operationally by Postgres HA (streaming replication + automatic failover via e.g. Patroni), which should keep actual outage windows in the seconds-to-low-minutes range. |
| 6 | **Network partition: worker can't reach scheduler, but is otherwise healthy** | Same as worker crash from the scheduler's point of view: no heartbeat, marked DEAD after 20s. | Covered in detail in doc 5.3 edge case #1. The critical piece: the worker-agent contract requires that upon reconnecting and receiving a `409` (stale epoch) on any call, **the agent must abort its currently running job locally** before re-registering, otherwise the same commit builds twice, on two workers, and both report success. This is a hard requirement on the worker-agent implementation, not just the scheduler. |
| 7 | **Network partition: scheduler replica can't reach Postgres, but other replicas can** | Advisory-lock renewal fails for that replica specifically. | That replica simply cannot become/remain leader (the lock requires an active session to Postgres) and falls back to serving read-only REST traffic and forwarding gRPC worker connections' heartbeats through to whichever store it *can* reach, or rejecting new gRPC streams so workers reconnect to a healthy replica (via client-side retry/redial, standard gRPC behavior). |
| 8 | **Duplicate heartbeats** (client retry, at-least-once network layer, or reordered delivery) | Not really "detected": designed to be a non-event. | Heartbeat handling is idempotent by construction: last-write-wins `HSET` on Redis, `UPDATE ... WHERE epoch=$epoch` on the batched Postgres flush. A duplicate or reordered heartbeat with an older or equal timestamp than what's already stored either overwrites with equivalent data (harmless) or is superseded (also harmless); there's no side effect that fires "per heartbeat received" that isn't itself idempotent (no counters incremented per-heartbeat, for instance). |
| 9 | **Duplicate job submissions** (client retries a `POST /jobs` after a timeout, unsure if the first attempt landed) | `idempotency_key` uniqueness constraint on `jobs` (doc 3). | Second submission with the same key gets a `409` with the *original* job returned, not a new one created. Clients are expected (and it's documented in the OpenAPI spec, doc 2) to always pass an idempotency key generated once per logical submission attempt, not per HTTP retry. |
| 10 | **Lost acknowledgement** (worker completes a build, reports result, but the response is lost, so the worker doesn't know if the scheduler received it) | Worker-side timeout on `ReportJobResult` with no ack. | Worker retries the same `ReportJobResult` call (same `job_id` + `assignment_epoch`). Scheduler-side handling is idempotent: if the job is already in a terminal state (`SUCCESS`/`FAILED`/`CANCELLED`) with a matching `assignment_epoch`, the duplicate report is a no-op ack, not a re-processing (doc 5.4's discard-on-epoch-mismatch branch also covers the case where the job moved on to a *different* assignment in the interim). |
| 11 | **Autoscaler failures** (cloud API call to add/remove capacity fails, or the autoscaler's own decision loop crashes) | Cloud API errors are caught and logged; failed scale-up/down attempts increment `autoscale_events{result="error"}` metric, alertable in Grafana. Autoscaler crash: it's a goroutine within the leader process, so a leader crash takes it down with everything else (recovered per scenario #1) and standalone deployment (if ever split out) would use the same leader-election pattern. | Autoscaling is explicitly **advisory, not load-bearing for correctness**: if the autoscaler is down entirely, the fleet keeps scheduling against whatever capacity currently exists; jobs simply queue longer rather than failing. Scale-down decisions are always conservative (never terminate a worker that's BUSY or has a job assigned to it; always drain first, see doc 9), so an autoscaler bug can make the fleet slow or wasteful but not unsafe (it can't, by construction, kill a worker mid-build). Repeated scale-up failures against a specific fleet provider trigger backoff (don't hammer a failing cloud API) and an alert rather than a silent retry loop. |
| 12 | **Split-brain during leader election** (two replicas both briefly believe they're leader; theoretically possible during a Postgres failover window) | N/A at the application layer; prevented structurally. | A Postgres advisory lock is exclusive by the database's own guarantee: Postgres itself will never grant the same advisory lock to two sessions simultaneously, even across a primary failover (the new primary doesn't have the old primary's lock table state carried over as "granted"; a session has to re-acquire). The remaining risk window is "old leader thinks it still holds the lock because it hasn't yet noticed its connection died"; mitigated by requiring the leader to re-verify the lock (a cheap `SELECT pg_try_advisory_lock(...)` style check, already held check) immediately before every assignment-committing transaction, not just once at startup. If that check ever fails, the replica immediately stops acting as leader. |
| 13 | **Postgres read replica lag** (dashboard/list APIs read slightly stale data) | Replication lag metric exported by Postgres, scraped by Prometheus, alertable. | Acceptable by design for read endpoints (`GET /workers`, `GET /jobs`): these are informational, not used for scheduling decisions. If lag exceeds a threshold, the API layer can optionally fail over those reads to the primary temporarily (feature-flaggable), trading load on the primary for freshness. |

## 6.1 What's *not* on this list, and why

**Byzantine/malicious workers** (a worker that registers with a valid token but then lies about its status or capacity) is a security concern, not a fault-tolerance one, and is addressed by not trusting worker-reported state for anything that matters beyond scheduling convenience: capacity/status feed the *candidate selection*, but the actual assignment is still gated by the Postgres CAS, and job results are logged/attributed to a specific worker+epoch permanently in the audit tables, so a misbehaving worker is detectable (and drain/ban-able) after the fact even though it isn't prevented from wasting one assignment slot before detection.
